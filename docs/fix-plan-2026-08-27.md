# Fix plan — findings from the first device test

From 12 annotated screenshots in `devs/debug/`, plus a code survey that found
several things the screenshots did not.

Ordered by one question: **does this corrupt tomorrow's data, or just annoy?**
Tomorrow is the first real restock run, and the run produces the dataset every
later feature reads. Wrong numbers recorded tomorrow are permanent.

Nothing here is built yet. Review and cut whatever you disagree with.

---

## Tier 1 — will corrupt tomorrow's data

### 1. Fill records a number the screen never shows

**Bug.** `after` is computed correctly, persisted correctly — and rendered
nowhere. `useCounting` exports it; `CountScreen` never passes it to `SlotRow`;
both steppers bind `before`. The green button is the *only* feedback Fill gives.

Your two screenshots prove it isn't a mixed-slot quirk: slot 11, single item,
capacity 5, reads `1` with Fill lit green. The omission is at the prop boundary,
so every slot type is equally blind.

**Fix:** render the after-count on every slot row, beside the before-count.

**Size:** contained.

### 2. Capacity can only be set estate-wide, never per slot

**Corrected after the `finish-machine-should-not-block-editing` screenshot.** An
earlier draft of this plan said capacity was uneditable anywhere. That was wrong
— slot 28 in that screenshot reads `capacity 10`, reached by editing the item's
**Par level** on the item screen. `basePar` seeds capacity for every slot the
item occupies, so editing it works.

The real gap is narrower: `setSlotConfig` — the per-slot override — has **no
caller in the app**, only tests. So par is all-or-nothing across fifteen
machines. You cannot say "this channel on L7 holds 20" without changing that
item everywhere.

Still matters, because combined with #1 it is silent: a channel physically
holding 20 records `after = 5` on Fill, and you cannot see it happen. But it is
now a workaround-exists problem, not a blocker — set par per item tonight and
tomorrow's numbers are right, as long as an item's real depth is the same in
every machine.

**Fix:** capacity field on the slot-edit sheet, already reachable from the
counting screen via `⋯`.

**Size:** contained.

### 3. `test-items` is in the live catalogue, on slot 50 of all fifteen machines

Visible in your Fill screenshot as a sub-row of slot 50. It is a **base**
placement, so it lands on every machine and makes slot 50 a phantom mixed slot
estate-wide. It also competes for Fill's preferred-item position.

**Fix:** you can do this yourself right now — Items → test-items → Delete item.
No code needed. Worth doing before tomorrow regardless of the rest of this plan.

**Size:** none, operator action.

### 4. Every slot reads RAN DRY on a machine with no history

On the first-ever visit there is no history, so every count seeds at 0 and every
row goes red. Tomorrow machine one opens as ~54 red rows all shouting RAN DRY.
Technically correct, useless as a signal, and it trains you to ignore the flag
that exists to catch lost sales.

**Fix:** suppress the ran-dry flag when a slot has no prior recorded level —
"never counted" is not "sold out".

**Size:** one-line.

### 4b. Finishing a machine must not lock it — it is only a flag

**A deliberate reversal of spec §7**, requested after device testing, not a bug.

Spec §7 says: *"Once finalized a visit is immutable — later corrections are
`Adjustment` records, never edits to history."* In practice, finishing a machine
and then noticing a miscount leaves you with a screen that silently swallows
every tap.

**Accepted, with the reasoning recorded.** Immutability protects an audit trail
across several people. This is one operator correcting their own miscount minutes
later — and the spec's own §5.3 already classes *"Miscount correction"* as "not a
stock movement", conceding that a wrong count is a data error rather than
history.

**Cost, stated plainly:** Phase 2's sales residual treats a finalized visit as the
closing record for a period, so an editable one makes that boundary soft. Every
record carries `updatedAt`, so edits stay traceable, and `touched` still
distinguishes a counted slot from a carried-forward one. Acceptable, but it must
be written into the spec rather than left as drift — §7 and §3.3 both need
amending.

**Fix:** `finalizedAt` becomes a marker, not a lock. Editing a finished machine
is allowed and re-stamps `updatedAt`. Keep the repository guard available for
Phase 2 if a genuine lock is ever wanted.

**Size:** contained, plus a spec amendment.

## Tier 2 — will slow you down or lose work tomorrow

### 5. Neither the count nor the map screen says which machine you are in

Fifteen near-identical maps, and the header is just `← Back`. On the counting
screen there is no header at all.

**Fix:** put the level in the header of both.
**Size:** contained.

### 6. No indication which machines are already finished

The machine list never looks at visits. A finished machine looks identical to an
untouched one, and re-entering it silently ignores every tap.

Already the top item in `known-gaps.md`.
**Size:** contained.

### 7. Delete sits where your thumb starts a count

**Your screenshot 
`should-not-allow-deleting-machines` reverses a request you made this morning,
and the code says you are right to.** The whole machine row is a "start count"
button, with Delete at its right edge in the same tap strip. Worse: on confirm,
the row re-lays out so **Confirm renders roughly where Delete just was** — a fast
double-tap deletes. Deleting a machine mid-run cascades its draft visit and every
count line, with no undo and no error message.

**Needs your decision.** Either:
- **(a)** Remove machine delete entirely. Simplest, and the roster is fixed at
  fifteen anyway.
- **(b)** Keep it but move it off the row — behind the map screen, say — so it is
  nowhere near the count target.

I lean to **(a)**, together with item 8. You are not asking to remove *item*
delete, and that one stays.

**Size:** one-line for (a).

### 8. The Add-machine form is not needed

Fifteen machines, fixed, created by the seed.

Note this makes the seed's own guard — which refuses to seed if any machine
already exists, precisely because this form invited hand-adding — redundant
rather than wrong. Leave the guard.

**Size:** one-line.

## Tier 3 — after tomorrow

### 9. Trays should read 1–6, not 10–60
Display label only; slot numbers stay 10–69. **One line, two places.**

### 10. Location column is noise
The seed writes `Level 2` as the label of machine L2, so it duplicates the level
on every row. Spec §4.1 defines a machine as being *at a location*
(`L7 · Lift lobby`), so **hide the label in the list — don't delete the field.**
**One line.**

### 11. Bottom nav sits under your scrolling thumb
Move to a header or a drawer. Nothing is lost when it's hit by accident — the
count screen restores from the draft — but it's jarring mid-count.
**Contained.**

### 12. Sixty items in one flat alphabetical list
Grouping by **tray** works today from existing placement data. Grouping by
**category** needs a new field on `Item` plus assigning 60 values. A search box
alone is much cheaper than either and may be enough.
**Needs a decision on which.**

### 13. Slot field should be a picker, not free text

**Careful — a literal single-choice control breaks real data.** Three of your
items legitimately occupy two slots: Nu Pure Water `48, 49`, Coke No Sugar
`56, 57`, Coke `58, 59`. A multi-select, or single-select with "add another",
gives you the picker without the regression.

The second half — reaching per-machine overrides from the item screen rather than
only at the machine — is straightforward once the picker exists.
**Needs design.**

### 14. Make the machine map editable from the map screen
`SlotEditSheet` already does item add/remove and can be reused. Worth pairing
with item 2, since capacity editing belongs in the same sheet.

Spec §5.1 deliberately put correction *on the counting screen* because "a
separate admin screen will never get used" — so this is **in addition to** that
path, never instead of it.
**Contained if it reuses the sheet.**
